# Phoenix game systems catalogue

| Field | Value |
|---|---|
| Status | Design inventory and proposal analysis; not a committed feature set |
| Last updated | 2026-10-05 |
| Scope | Rules governing participation, information, world behaviour, combat, operations, scenarios and continuity |

These systems make the [ship capabilities](./ship-systems.md) interact and give their operators reasons to act. The [proposal GDD](./README.md) will select coherent combinations rather than equate a longer feature list with a better game. Networking architecture remains outside the redesign; session and multi-ship rows describe player experience only.

**Current**, **Plan**, **Research** and **Proposal** use the same definitions as the ship catalogue. **O** means ongoing work/awareness; **E** means event-driven intervention. Activity and risk notes are **proposal analysis**, not observed playtest results. Stable G identifiers support later comparison; they are not PASM component names.

## Using this catalogue

Select a small coherent system set only after tracing who discovers a change, who decides, who executes, what the rest of the crew does while it runs, and which AI systems relieve basic execution. A candidate with no changing decision can remain passive hardware without receiving a dedicated player. A candidate that creates several tightly timed demands for one officer needs reserves, automation or a different bundle.

Use G093 to compare quiet travel, observation, negotiation, external work, layered combat, damage and recovery. The proposal should earn breadth through these activity tests rather than simply ship every row.
