# Device matrix and baseline workflows (#1421)

**This is a HITL preparation kit, not the acceptance run itself.** Issue
#1421 is scoped as: *prepare* the device/browser/viewport/scale matrix this
repository can already stand behind, ship the shared fixtures other T3
issues and their acceptance kits import, and leave explicit blanks for what
only a human, on real hardware, can supply. **No box below is checked by
this issue.** A human records actual devices, browsers, the landscape
tablet's real viewport and room viewing distance, then runs the task
scripts and checks the boxes, dated, on a specific build revision.

Parent PRD: #1418 (T3 presentation, comfort and integrated GM usability),
user stories 1, 7, 18, 22, 33. Its Testing Decisions: *"Before the affected
issues become ready, record the supported browser/device matrix, actual
landscape-tablet viewport, smallest supported split-pane geometry and room
viewing distance; make those reproducible acceptance inputs rather than
guessed measurements."* This document and
`tests/fixtures/device-matrix.mjs` are that recording.

### 1.2 Native split-pane floor

`src/native_host/setup_accessibility.rs`:

- `MIN_CONSOLE_LOGICAL_WIDTH_PX = MIN_CONSOLE_LOGICAL_HEIGHT_PX = 320` logical
  px — the smallest pane a console stays operable in, **at text-scale 1.0×**.
  The width floor scales linearly with the text-scale multiplier (so 640px at
  `SUPPORTED_TEXT_SCALE_MAX = 2.0×`, raised from 1.5× by issue #1422); the
  height floor is fixed,
  because consoles absorb extra vertical content by scrolling
  (`overflow-y: auto`), not by growing the floor.
- `MAX_PANES_PER_STATION = 2` (`src/native_host/bridge_profile.rs`) — a
  Station may split into at most two panes on one monitor; default split
  direction is side-by-side (`PaneSplit::SideBySide`,
  `src/native_host/bridge_layout.rs`).
- This floor and the reflow arithmetic built on it are already covered by
  pure, hardware-free CI tests (`src/native_host/setup_accessibility_tests.rs`)
  and by the **real-monitor** walkthrough in
  `docs/acceptance/1128-accessibility.md` — this kit does not duplicate that
  one; run it for the native multi-monitor acceptance and cite its result
  here (§4) rather than re-deriving it.

### 1.3 Browser engines

- **CI-asserted today**: `tests/smoke/playwright.config.js` runs exactly one
  browser engine — Chromium (`devices['Desktop Chrome']`), in two projects
  (the message/DOM suite, and a `render` project that adds a software WebGL2
  context via SwiftShader for the `.render.spec.js` viewscreen-draw tests).
  No Firefox/WebKit project exists in this config.
- **No other documented browser-support list exists in this repository.**
  `grep`-ing `docs/`, `gui/`, `CONTEXT.md` and `AGENTS.md` for a supported-
  browser statement turns up only per-incident mentions (e.g.
  `docs/acceptance/1335-native-lobby.md`'s note that the native host's
  embedded WebKit view has its own keyboard-focus behavior) — not a
  maintained matrix. **This is a real gap, not an oversight this document
  papers over**: §2 asks the operator to record which real browsers (and
  versions) the acceptance run actually used, because the repository cannot
  supply that list on its own.
- Player consoles are plain HTML/CSS/JS (`AGENTS.md`: "the client is pure
  HTML/CSS/JS — no client-side WASM"), so they carry no Chromium-only
  dependency by construction; the host/Viewscreen and native GM path run
  Bevy/WASM or the Ultralight SDK respectively, which is where an engine
  difference is most likely to show up first.

### 1.4 Phone console / phone Viewscreen / landscape-only GM boundary

PRD #1418, "Supported surfaces and enlargement":

- **Player consoles**: browser phone, tablet, PC, **and** native Station
  panes (including split-screen). **Implemented and tested today** — see
  the portrait AND landscape phone fixtures in §1.1 (`hero-bar-responsive`'s
  390×844 portrait case exercises the Station bar's phone-portrait form
  directly).
- **Viewscreen**: full display surfaces, plus "a secondary phone experience"
  (PRD user stories 18–21: phone-Viewscreen text scaling for menus/overlays,
  contrast, Reduce effects, and the Level-3 AI-to-AI Coordination compact/
  tap-to-expand exception). **This secondary phone-Viewscreen surface does
  not exist in the repository yet** — it is a requirement for a *later* T3
  implementation issue, not something #1421 can record acceptance evidence
  for. Do not check it off until that issue lands; this document only
  records the design commitment so its acceptance kit inherits the same
  matrix.
- What **does** exist today is `server.html` (the shared Viewscreen/GM host
  document) forcing landscape on a phone-shaped screen it is itself running
  on (`data-phx-force-landscape`, added in `384ca3f7`): a phone used *as the
  host machine* gets rotated into the same landscape layout as everyone
  else, rather than falling into `host-landing.css`/`host-lobby.css`'s
  compact portrait rules (which remain live, unguarded, for `client.html`
  player consoles). That is a different thing from the PRD's phone-Viewscreen
  *companion display* feature above — do not conflate the two when this
  section is filled in for a later issue.
- **GM**: PC and tablet, **landscape only**, web today; native GM is T4 M6
  (PRD #930), out of this PRD's scope to bring forward. No phone GM, no
  portrait-tablet GM.
  - **What is actually enforced**: `server.html`'s GM-only controls
    (`#gm-start-controls`, `#lobby-gm-group`) are populated only once the
    page has been admitted with the GM role; ordinary player phones running
    `client.html` are never issued an action capable of reaching them. That
    is an **admission-path** limit (a phone player is never a GM), not a
    device-class/viewport check on the GM path itself.
  - **What is a documented decision, not a coded gate**: this session found
    no runtime check that refuses a narrow or portrait viewport specifically
    *because* the page has been admitted as GM. The two GM Playwright
    fixtures that exist (1280×720, 1440×900, `gm-layout.spec.js`) are both
    landscape desktop-class sizes, and no GM-suitable compact/portrait layout
    is authored anywhere in `gui/gm-workspace.css` — so "no phone/portrait
    GM" holds today by **absence of support**, not by an enforced refusal.
    Record this honestly in any acceptance note: a GM *could* technically
    open `server.html` on a narrow viewport and get an unsupported, untested
    layout, not a friendly refusal screen.

## 3. Repeatable task scripts

Each script names the shared fixtures it uses from
`tests/fixtures/device-matrix.mjs` — import it once (`import { DEVICE_MATRIX,
TEXT_SCALES, BROWSER_ZOOMS, DENSE_CONTENT } from
'../fixtures/device-matrix.mjs'`) rather than retyping viewport numbers or
long dialogue strings by hand, so a future automated version of these tasks
and this manual run start from the identical inputs.

Run each task once per recorded device from §2 (at minimum: one phone, the
landscape tablet, the native rig, one desktop browser window) and record
pass/fail/note per device in §4.

### Task A — Settings (any player-console surface)

1. Open the console **Settings → Accessibility** tab.
2. Load a station whose help/manual panel is open, so a `DENSE_CONTENT.consoles`
   entry (e.g. `help.navigation.3.body`, 194 characters) is on screen.
3. Step the text-scale slider through every stop in `TEXT_SCALES` that the
   build actually exposes today (`1`, `1.5` — `2` is PRD #1418's target for a
   later issue; if the slider now reaches 2.0×, exercise it too and note that
   the ceiling has moved). At each stop: no label clips, no control overlaps
   another, the panel wraps/stacks/scrolls rather than shrinking text.
4. Cycle contrast (`default` → `on` → `off`) and reduced motion the same way;
   confirm the change is visible immediately (live preview) without a reload.
5. Change one setting, use its own **Reset**; confirm only that setting
   reverts. Change several, use **Reset all**; confirm all presentation
   settings revert and nothing outside presentation (identity, save data,
   bindings) is touched.
6. Reconnect (or restart the client) and confirm the chosen values survived.

### Task B — Console (player device: phone / tablet / desktop / native pane)

1. Claim a station with a Comms panel available.
2. Load the `DENSE_CONTENT.comms` entries (three real long Falling Skyway
   dialogue bodies, 321–463 characters, e.g.
   `world.falling_skyway.comms.window_opens_short`) into the message list —
   via the Falling Skyway world, or by pasting the same text into a GM
   Comms send if a faster path is available.
3. At each `TEXT_SCALES` stop the build exposes: confirm the message remains
   readable, the current target/status readout stays visible, and every
   action button stays reachable (scroll, don't clip).
4. On a native pane specifically: repeat at the narrowest split-pane width
   the rig can produce, and compare against the `native-split-pane-floor`
   entry in §1.2 — a pane at or above 320 logical px (scaled per §1.2's
   formula) should preserve the console; below it, expect (and confirm) the
   documented **TOO SMALL** report from `phoenix-host --setup`, not a silent
   broken layout.
5. Separately from the in-app slider: set the *browser's own* zoom through
   each `BROWSER_ZOOMS` stop (100/125/150/200%) and repeat step 3. Record
   browser + version (§2) — this is the "verify browser zoom separately"
   requirement in PRD #1418, and is not the same code path as the in-app
   text-scale slider.

### Task C — Viewscreen / GM (landscape surfaces only, per §1.4)

1. Open `server.html` as the Viewscreen/GM host at each of
   `desktop-1280x720-gm` and `desktop-1440x900-gm` from §1.1 (and the
   landscape tablet's real viewport from §2, once recorded).
2. Load the `DENSE_CONTENT.gmLists` entries at their `repeatHint` volume
   (e.g. ~12 rows built by repeating `server.gm.objective.preview_complete`
   or `server.gm.mission.skip_result_timed_out` across different
   targets/timestamps — the String Table intentionally has no 12-near-
   duplicate rows; the volume is scenario data, the wording is the fixture)
   into the GM Objective panel / mission log / activity feed.
3. While new entries keep arriving, focus and begin reading one row.
   Confirm: reading position and focus do not jump, a new-item count and
   **Return to live** appear rather than the list silently reordering under
   you, and any critical connection/recovery banner stays visible separately
   from the held list.
4. Confirm the page stays landscape-locked on the phone-shaped case (if one
   is available) — `data-phx-force-landscape` should rotate/relayout rather
   than fall into `host-landing.css`'s portrait rules — and record that this
   exercises the *host-forced-landscape* behavior in §1.4, not the (not yet
   built) phone-Viewscreen companion display.
5. Native multi-monitor GM: do not duplicate here — run
   `docs/acceptance/1128-accessibility.md` and cite its dated result in §4.

### Task D — The Viewscreen's own Display settings (#1427)

Endpoint-owned text size and contrast. The browser half is covered by
`tests/smoke/viewscreen-settings-presentation.spec.js`; **the native half is
not automatable at all** — an Ultralight window on a real Windows machine,
restarted — so it is a human check:

1. On the NATIVE host, open the settings cog on the viewscreen window and
   select **Display**. Set text size to 200% and contrast to **More**.
   Confirm the landing, the world picker, the join panel and the lobby chrome
   all enlarge and re-contrast *while you watch* (live preview), and that the
   3D view behind them is unchanged in size and framing.
2. Confirm the panel wraps/stacks/scrolls at 200% rather than clipping: every
   control on the tab is still reachable, and **Escape** closes the panel and
   returns focus to the cog.
3. **Quit the host and start it again.** The surface must come back up at
   200% / More *before* you open the menu. This is the property the file
   `%APPDATA%/ProjectPhoenix/viewscreen-presentation.toml` exists for; if it
   is absent after step 1, the host could not write it and the log says so.
4. Load a *different* scenario, then a saved session. The Display settings
   must not move, and nothing about them may appear in the save.
5. Press **Reset Contrast** (text size stays at 200%), then **Reset Display
   Settings** (both return to following Windows). Confirm your bridge layout,
   host bindings and saved games are untouched.
6. Repeat step 1 with Windows' own text-size and high-contrast settings
   changed while the Display tab is set to **System**, to confirm the
   follow-the-machine state — the same machine preferences
   `docs/acceptance/1127-windows-preferences.md` records.

Record the result in §4 with `Task D` and the build SHA.

## 5. What the automated half already covers

`tests/client/device-matrix.test.js` (vitest) pins the **shape** of
`tests/fixtures/device-matrix.mjs` — not the acceptance itself:

- every `DEVICE_MATRIX` entry is well-formed and **names a non-empty
  `source`** (the no-fabricated-device-minimums rule, made checkable);
- ids are unique; the PRD's two starting regression cases (390×844,
  1280×720) and the native split-pane floor (320×320) are present;
- `TEXT_SCALES`/`BROWSER_ZOOMS` are non-empty ascending numeric lists;
- every `DENSE_CONTENT` descriptor id is a **real row in
  `assets/strings/strings.csv` today**, checked live via `gui/strings.js`
  `has()` (loaded from the actual CSV by `tests/client/setup-strings.js`) —
  so a renamed or deleted string id fails this test rather than silently
  going stale in a fixture nobody re-reads.

Existing responsive/accessibility Playwright specs already exercise several
of the §1.1 viewports against real layouts (`scope-responsive.spec.js`,
`hero-bar-responsive.spec.js`, `console-redesign-accessibility.spec.js`,
the three `cruiser-*-responsive.spec.js` files, `lobby-responsive.spec.js`,
`gm-layout.spec.js`, `accessibility-contrast.spec.js`,
`accessibility-reduced-motion.spec.js`, `accessibility-native-defaults.spec.js`)
— none of them import `tests/fixtures/device-matrix.mjs` yet (they predate
it); a later T3 issue that adds new responsive/accessibility coverage should
import the shared lists above instead of hand-copying viewport numbers again.

Issue #1422 is the first that does. It adds:

- `tests/smoke/text-scale-power-workflow.spec.js` — the Power allocation
  workflow carried through the shell, its console iframe and the allocation
  controls, driven from `DEVICE_MATRIX` × `TEXT_SCALES` (100/150/200%), with
  browser zoom as a **separate** pass over `BROWSER_ZOOMS` (emulated the way a
  browser does it: CSS viewport ÷ zoom, device pixel ratio × zoom) and contrast
  / forced colours through `page.emulateMedia`. It asserts reachability of every
  control and status, that nothing shrinks as the scale rises, and that the
  authoritative order a control sends is unchanged by the text size.
- `tests/client/accessibility-200-percent.test.js` — the profile behaviour
  behind it: defaults, explicit override, migration, reconnect, live preview,
  per-setting reset and the presentation-scoped Reset all.

Note the split-pane row is a per-pane **floor quoted at 1.0×**, not a device:
`MIN_CONSOLE_LOGICAL_WIDTH_PX` scales with the text multiplier, so the smoke
spec exercises it at 320 × the scale under test (640 px at the 200% ceiling)
rather than asserting a 320-wide pane at 200%, which the Rust contract in
`src/native_host/setup_accessibility.rs` explicitly reports as TOO SMALL.
`docs/acceptance/1128-accessibility.md` remains the native multi-monitor HITL
kit for the split-pane floor and its reflow/focus/contrast behavior; this
document does not duplicate it.

Issue #1425 adds `tests/smoke/engineering-operations-text-scale.spec.js` —
Engineering + Operations (allocation, Repair, Tractor, Umbilical, Dock, and
the External-dispatch "Transport" mechanism) carried through their DEDICATED
and COMPOSITE Station surfaces at 100/150/200%, `tablet-650x450` and the
native split-pane floor explicitly, browser zoom and forced colours. Its own
file-top comment carries the full per-hull family-variant inventory (which
of Repair/Tractor/Umbilical/Dock/`[repair.external_dispatch]` each hull's
`assets/entities/alliance_*.toml` actually authors, and which document
renders each) rather than duplicating it here. It also fixes a real bug this
matrix's own `tablet-650x450`/`native-split-pane-floor` rows caught: several
Operations-panel status rows (`.dock-status`, `.tractor-status`,
`.dispatch-status`, `.tow-load-target`) sat in a `display: flex` row next to
a button with no `min-width: 0`/wrap budget, so a long world-entity name (an
unbounded-length string) either overflowed sideways or — once the button
alone could consume the row's entire width at 200% text on a narrow pane —
collapsed to zero rendered width instead of wrapping to its own line; and the
destroyer/battleship Repair-team roster (`ph-repair-teams`) could render at
literally zero height at the tightest geometry, because it was the one flex
child in its column with `min-height: 0` competing against three auto-height
siblings that never shrink. `docs/acceptance/1421-device-matrix.md` §2's
landscape-tablet viewport, once an operator records it, is a fifth row worth
adding to that spec's own `CARRIED_ON` list alongside the four already there.
