AD15 · Selected A

Derived trees can change parameters and structure

Override parameters and add or replace named states, tasks and transitions. A turret variant can add a supported jam task to its inherited Engage state. Validate the resolved tree as a whole, including inherited and local contributions.

Stable node IDs, explicit overrides and an inherited/local-origin view are proposed implementation safeguards. Exact merge, removal and conflict semantics remain to be specified. Structural changes still use the game's supported node types.

Definition reuse and runtime ownership are separate. Two Systems using the same base or linked subtree retain their own knowledge and execution state. Inheritance does not extend the supported input/output vocabulary.

AD16 · User-selected direction

A reference node calls another reusable tree

A base or derived tree can contain a reference node that calls another state tree. Inheritance changes the definition being used; a reference node invokes reusable behaviour during execution. The call remains inside the same System's AI, with its permitted Console context and existing control authority.

Proposed Workshop support: select the referenced asset, bind supported parameters and inspect its definition; validate the result against the caller's inputs, outputs and equipment. Calls can span simulation ticks. No global mutable tree instance supplies private state to unrelated callers.

AD17 · Selected A The tree reacts immediately; machinery may take time

An eligible parent transition interrupts the affected referenced subtree when the AI processes the new permitted input. It changes state and can issue the new order without waiting for the old call or hardware transition to finish. For example, the tree can choose a new target while the turret is still traversing toward the old one.

Immediate reaction adds no wait for subtree completion. Information delivery, S062's simulated reading time where applicable and deterministic scheduling still apply. Completed physical effects are not rewound. Detailed completion outcomes, exit cleanup, channel persistence, re-entry and cancellation rules remain to be specified.

Proposed status contract: show requested state separately from observed actual state and known transition or blocking reasons. Apply ordinary knowledge limits; a stalled mechanism does not automatically reveal an undiagnosed cause.

AD18 · Selected user direction Top-down execution; the last write wins

Execute in deterministic top-down order. When several active nodes write the same System command channel, the last write takes priority. A later target replaces the earlier target; it does not replace unrelated attack or jam values. No numeric output-priority field is needed for this rule.

Proposed traversal: active parent work precedes descendant work, tasks and siblings retain their authored order, and a referenced tree executes at its call site's position before the caller continues. Workshop shows that resolved order across inherited and referenced definitions. Asset order is semantic data, independent of runtime container iteration or incidental editor coordinates.

Proposed mapping: resolve pending channel writes before mechanisms consume the admitted final intent. An overwritten request must not briefly fire a weapon or consume resources. One-shot actions and discrete jobs need separate contracts; this rule cannot undo a sent message or a launched projectile. It also does not select how competing transitions are chosen.

AD19 · Selected A Later nodes see earlier internal writes

Private AI memory and pending System command values update during the ordered evaluation. A parent task can choose a target and a later task can read that pending target to decide whether to jam it in the same pass. The last write still wins separately for each command channel.

Candidate validation and test-preview requirements

  • Resolve asset inheritance and reference nodes. Reject inheritance cycles; specify recursive-call policy separately from ordinary state-transition loops.
  • Check declared node types, input/output types, supported System channels, state references and permitted binding sources.
  • Show the resolved tree, inherited/local origins, reference-call path, execution order, each node's read values and each channel's write sequence/final writer, using the same evaluator as the game.
  • Test separate callers using one definition, nested calls and interruption, ordered competing outputs, missing/old observations, shared attack/jam operation and human/AI handoff. Check that changing unrelated storage iteration cannot change the winning writer and that overwritten values produce no transient actuation.
  • Verify later nodes can read earlier private-memory and pending-command writes in the same pass while captured observations remain unchanged. Later writes must not silently rerun earlier nodes or leak into other AI instances.
  • Verify a new permitted order can interrupt a call before its physical work finishes, while actual traversal/ramp obeys normal limits and completed effects remain. Do not equate a successful tree transition with physical completion.

These are proposed acceptance concerns for later implementation, not tests run or proof that the editor exists. Migration must account for current stateless policies and named-state machines while retaining their established command and knowledge boundaries.

Reference model and current Phoenix groundwork

Epic describes StateTree as hierarchical states with entry conditions, tasks, transitions and data bindings. Active ancestor states can contribute tasks; transition rules govern reselection. Its published extension points include custom node implementations, which Phoenix excludes from Workshop. See Epic's StateTree overview (checked 12 October 2026).

Epic also documents linking a reusable tree asset from another tree. That supports the reference for modular reuse; it does not establish the exact inheritance semantics Phoenix will use. See Epic's external StateTree guide. Phoenix's structural inheritance and reference-node calls are user-selected requirements recorded in AD15–16.

Current policy.rs implements typed action verbs, prioritised per-channel rules and optional named-state machines with private memory. host.rs requires AI control and a declared policy before resolving an action. The examined machine schema is a list of named states; this does not establish the proposed hierarchical, reusable and inheritable assets.

AD18 deliberately selects execution-order precedence for the new trees, replacing the earlier recommendation to extend numeric output priorities. Migration must translate intended behaviour explicitly; the current rule winner and a new tree's last writer are different contracts.

The design should build on the individual-System AI model, existing module boundaries and Workshop document/validation/Test workflow. Full decisions are in the architecture brief; the broader context remains the gameplay proposal.

Selected: supported mechanisms, configurable per-System AI state trees, structural inheritance, reference-node calls, immediate tree reaction with potentially gradual physical response, deterministic top-down writes with the last write winning, and visibility of earlier internal writes to later nodes. AD20 selects compact status and repair reporting from fully AI-operated Consoles; AD21 selects a shared work list updated by reports and team completion messages. Detailed merge/execution/data contracts remain open. No code, PASM design or networking changes are made by this report.
