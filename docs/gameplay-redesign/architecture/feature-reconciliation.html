Project Phoenix / Architecture synthesis / 13 October 2026

Reconcile the features into a small mechanism library

Keep the selected gameplay. Build it from reusable mechanisms, combine those into operable Systems, and give world activity and supporting tools clear homes.

Existing gameplay decisions preservedGrouping proposal for review114 game + 102 ship entries mapped

This pass defines responsibilities, reuse and information flow. Detailed System rules, numerical tuning, exact schemas and implementation sequencing come later. These twelve mechanism families are a proposed organisation of the code, not twelve new crates or twelve player stations.

Delivery follows the approved incremental implementation roadmap. The mechanism groupings below remain the design reference for per-increment specifications.

Each family groups reusable data and focused processors. Share contracts where meanings match; keep domain-specific calculations inside the relevant processor. In particular, a shared capacity does not make heat, fuel, ammunition and information interchangeable resources.

Check the reuse with concrete configurations

Weapon + jammer turret: one System, one target channel and shared mount/traversal; weapon and jammer components read their supported attack/jam channels and draw actual resources.

Beam bank, twin gun and missile rack: the same weapon family with different delivery modes, barrel cycles, resource requirements and effects.

Broad scanner + focused array: separate Systems using common sensor processing; their permitted observations can feed the same radar screen.

Deployable turret and decoy: ordinary entity configurations. One fits a weapon; the other fits spoofing and lifetime behaviour. Neither needs a separate deployable simulation.

Starbase repair service: facility Systems, stocks and workforce teams use the same condition, inventory and work mechanisms as a ship.

Repair, boarding and away mission: shared personnel and job records, with different supported work steps, constraints and outcomes.

Data flows through stable boundaries

Inside the simulation

Supported components are typed records. Shared engine processors operate on the applicable records, with explicit service, spatial and information references. Requests and resolved resources connect physical mechanisms; supported events connect consequences. The engine owns processing order.

A System is the control and composition boundary. It does not require an object that recursively updates every component, nor a network message for each local data change.

Across connections

Clients send intent through the existing reliable command path and render authorised projections and results through the existing message/snapshot classes. Browser clients remain HTML/CSS/JS. Current multi-host replication, joining, recovery and GM control paths stay intact.

In-world Comms links are gameplay: range, interference, encryption and knowledge affect delivery. They do not disconnect players or replace Phoenix transport. New state must integrate with existing replication/persistence contracts when implemented.

Runtime / Transport / PlatformKeep reusable infrastructure game-independent. This proposal does not replace rendezvous, transport lanes, session delivery, fleet networking or host services.

Gameplay, World and Session remain sibling domains without sibling or parent imports. Shared vocabulary goes through established contracts; Simulation supplies live inputs and composes their effects. The twelve mechanism families describe responsibilities across these owners, not a new dependency tree.

Workshop exposes composition rather than new programming

Use visual views of the same authored data: entity/deck/compartment layout; fitted Systems and component templates; resource and permitted-information connections; Station/Console assignment; screen/widget layout; supported state trees and references. Reuse validation, history, preview and disposable Test. Authors choose supported mechanisms, parameters, bindings and reusable templates; new processor or AI-node implementations remain code work.

The grouping review needs to establish that these views cover the design. Exact file syntax, IDs, validation messages, drag-and-drop interactions and migration strategy can be designed afterward.
